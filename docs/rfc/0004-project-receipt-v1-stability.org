#+title: RFC 0004: Stable Gerbil Project Receipt v1
#+startup: overview

* Status

Normative v1.

* Decision

=gerbil-bazel.project-receipt.v1= is the stable public receipt emitted by every
Gerbil project action. Internal execution capabilities do not create a new
project receipt version.

The following six fields are required and retain their original meaning:

- =schema=
- =status=
- =durationSeconds=
- =libraryOutputRequired=
- =packageIdentity=
- =packageRevision=

The two package-named fields are retained to keep the published v1 shape
stable.  Current generic project producers emit empty strings.  They do not
define a second package graph: =gerbil.pkg= and =gxpkg= own package semantics,
while repository pins and Bazel content inputs own reproducible source
identity.

Three optional extension fields are reserved in v1:

- =resourceGuard= contains a typed
  =gerbil-bazel.resource-guard-receipt.v1= value when the action uses the
  Scheme process guard.
- =buildReceipt= contains the build-script-owned JSON value captured through
  =receipt_line_prefix=.
- =dependencySourceResolutions= contains the deterministic postorder projection
  of direct and transitive
  =gerbil-bazel.dependency-source-resolution-receipt.v1= artifacts declared by
  the project graph.

No producer-owned receipt replaces the outer Gerbil-Bazel receipt.

* Compatibility contract

| Concern | v1 rule |
|---------+---------|
| Required identity | The original six fields are always present. |
| Producer JSON | Nested under =buildReceipt=; its schema remains producer-owned. |
| Resource policy evidence | Nested under =resourceGuard=; absent when no guard runs. |
| Dependency source evidence | Nested under =dependencySourceResolutions=; absent when the project graph declares no source-resolution receipts. |
| Unknown top-level fields | Rejected by the normative JSON Schema. |
| New execution capability | Uses a reserved optional field or requires a separately approved project receipt version. |
| Existing reader | A reader consuming only the six required fields remains valid. |

* Atomic cache semantics

The receipt is an output of the same declared project action as the compiled
tree. Declared sources, transitive project tree artifacts, toolchain capability,
and guard implementation participate in the Bazel action key. Repository pins
materialize the revisions declared by the consumer's canonical dependency
manifest. Changing one dependency input invalidates that project and its
reverse-dependent closure; an independent project remains reusable.

* Exactly-once dependency source projection

=GerbilProjectInfo= carries a postorder depset of source-resolution receipt
artifacts.  =gerbil_project_compile= merges the direct labels declared by
=source_resolution_receipts= with every dependency's transitive depset.  Bazel
artifact identity therefore removes duplicate paths before the action writes
one deterministic manifest.  The native Scheme receipt writer reads that
manifest once and adds one ordered =dependencySourceResolutions= array to the
outer receipt.

Gerbil-Bazel validates the receipt producer's stable structural contract.  It
does not reinterpret the consumer's canonical dependency policy.  A downstream
consumer such as POO Flow remains responsible for rejecting a resolution mode,
URI, revision, digest, worktree state, or logical-package set that disagrees
with its own contract.

* Adaptive project-child worker boundary

The Scheme resource guard computes the project child's =GERBIL_BUILD_CORES=
after =gxi= has started.  This location is deliberate: =gxi= initializes its
own worker environment, so a Bazel-declared =GERBIL_BUILD_CORES= value is
preserved first as =GERBIL_BAZEL_REQUESTED_BUILD_CORES=.  The guard then caps
the requested value by the observed logical CPU count and the RSS-derived
memory-core limit.  Runnable-process saturation remains an advisory and never
silently changes the selected worker count.

* Failure semantics

Failed Bazel actions report their typed guard receipt in the action log because
failed declared outputs are not cacheable. Successful actions store the same
guard value under =resourceGuard=. Host-pressure admission failure, RSS limit,
and deadline termination therefore remain observable without manufacturing a
successful project receipt.

* Upstream-native compiler modes and executable-link capabilities

The stable project receipt version is independent from native toolchain
normalization.  Gerbil-Bazel does not copy or rewrite the installed
=gambuild-C=: discovery reads its literal =C_COMPILER= declaration and queries
=FLAGS_DYN= and =FLAGS_OBJ= without writing the installation.  A generated
executable-path =GERBIL_GSC= launcher uses Gambit's public =-cc=,
=-cc-options=, and =-ld-options= interfaces.  Because =-cc= clears Gambit's
configured mode flags, implicit or explicit dynamic compilation restores the
complete =FLAGS_DYN= value before appending any platform extra, while =-obj=
restores the complete =FLAGS_OBJ= value.  =-c=, =-link=, and =-exe= pass through
without a wrapper-added compiler override.  Gerbil's public =GERBIL_GCC=
boundary remains the final executable linker.  On Darwin it selects Xcode
Clang and dynamic compilation appends =-Wl,-undefined,dynamic_lookup=; Linux
restores the installed producer flags without the Darwin extra or a separate
final link driver.  This normalization does not change the project receipt v1
schema.

This division matters for a Gerbil installation produced by GCC 16: replacing
the producer globally sends GCC-only optimization flags to Clang, while leaving
the final executable link on GCC can fail against Darwin's host link model.
Using the two upstream environment hooks preserves the runtime ABI without
mutating an installed upstream artifact.

** Compiler failure receipt v1

The materialized =GXC=, =GERBIL_GSC=, and =GERBIL_GCC= wrappers emit typed
evidence when an upstream compiler stage returns a nonzero status.  The action log
receives one =gerbil-bazel.compiler-failure-receipt.v1= record containing the
driver, mode, original exit status, a NUL-delimited argument manifest encoded
as hexadecimal, and a whitelisted environment manifest encoded the same way.
Each existing compiler or linker input also receives a
=gerbil-bazel.compiler-input-receipt.v1= record with its byte size and SHA-256
digest.  The native Gerbil compiler driver uses =compile-driver=, GSC modes are
reported directly, and the executable linker uses =final-link=.

These records are failure-only observability.  They do not retry the compiler,
change upstream scheduling, mutate an installed Gerbil/Gambit artifact, or
extend the stable project receipt v1 schema.  As required by the failure
semantics above, an action-local handoff stores them as valid JSON Lines and
the project runner restores their typed log prefixes before the bounded build
tail.  Receipt collection is best effort and never replaces the original
compiler exit status.  The records remain failure evidence rather than
cacheable declared outputs.

The standard regression =//tests/smoke:gxpkg_native_package_test= starts from a
real =gerbil.pkg=, invokes the public =gxpkg= wrapper, delegates to
=std/build-script=, compiles a native =log= reference, links an executable, and

=gerbil-utils= project then passed in 51.606 seconds with a 30.25-second Gerbil
action, and =//scheme:compile_receipt_v1_test= passed in 187.355 seconds with a

The follow-up 2026-07-19 compiler-mode acceptance diagnosed the cross-platform
CI failure caused by =-cc= clearing installed mode flags, then verified the
read-only restoration path.  All 16 forced Bazel tests passed in 19.296
seconds; the standard native package fixture passed in 10.2 seconds.  A POO
Flow command-line module override then rebuilt the real =gerbil-utils= package

receipt passed, including a 42-second atomic-cache phase, and the final
synthetic auto and prebuilt provider receipts passed in 15 and 16 seconds.

* Versioning rule

Version 2 is not introduced by this RFC. A future project receipt version needs
a demonstrated incompatible semantic change, a migration plan, parallel reader
coverage, and explicit approval. Field growth alone is not sufficient.
